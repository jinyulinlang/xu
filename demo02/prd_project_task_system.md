# 项目任务管理系统 PRD

下面的文档基于你提供的 `原始需求.md`，并按照 `prd模板.md` 的结构整理。

## 1. 引言（背景、目标用户、产品愿景）

背景
- 公司/团队有大量项目需要管理，常见痛点：任务粒度不足、任务分配与进度同步不及时、没有统一的可视化进度面板、缺乏自动预警与负责人提醒机制。

目标用户
- 一线领导（项目经理/部门负责人）：需要把项目拆成任务、分配并追踪执行、设置里程碑、获取预警。
- 团队成员：接收任务、更新任务状态与进度、上传备注与交付物。
- 高层/PMO：看整体项目组合状态、关键风险、交付率与时间偏差。
- 系统管理员：配置通知规则、权限、组织结构与集成。

产品愿景
- 打造一款轻量而可扩展的项目任务管理平台，实现“从项目到任务、从计划到实绩、从预警到闭环”的全流程可视化与自动化提醒，降低沟通成本，提高交付可控性。

## 2. 用户故事与场景描述

主要用户故事（优先级标注为 P0/P1/P2）
- P0：作为项目领导，我希望把一个项目细化成多个任务并分配给不同成员，以便明确责任（验收：任务创建、分配、责任人可见）。
- P0：作为成员，我希望能对分配到我的任务更新状态与进度百分比，并添加备注或附件，以便同步实际情况（验收：状态更新记录、历史可追溯）。
- P0：作为负责人，我希望系统在任务延期或关键里程碑风险升高时自动预警并通知负责人和团队，以便及时采取措施（验收：预警触发并发送通知）。
- P1：作为高层，我希望看到项目进度可视化（甘特/看板/里程碑视图）以便快速评估项目健康（验收：视图可切换、筛选、导出）。
- P1：作为 PMO，我希望能查看项目用时、完成率与依赖关系报告，以便做资源调整（验收：报表导出、依赖图）。
- P2：作为系统管理员，我希望配置通知规则（例如：提前 N 天/逾期/进度落后阈值）并管理权限与部门结构（验收：规则管理页、权限控制）。

典型场景
- 领导在立项后创建项目并设置计划开始/结束时间，拆分任务并设置依赖关系；成员每日更新进度；系统在任务逾期前 3 天发出预警；任务完成后系统记录实际完成时间并计算用时及完成率。

## 3. 产品范围与功能列表（scope & Features）

范围说明
- MVP（版本 1.0）覆盖项目、任务、用户/组织、进度更新、基本可视化（看板与甘特简版）、通知预警、导出报表与权限控制。
- 后续版本扩展高级报表、深度 AI 助手、多周期自动排期、第三方工具集成（例如：LDAP、邮件、企业微信/钉钉、Jira/Azure DevOps 同步）。

功能清单（按模块与优先级）
- 项目管理（P0）
  - 创建/编辑/归档项目（字段：项目名称、部门、负责人、成员、计划开始/结束时间、备注、里程碑列表）
  - 项目仪表盘：总体完成率、关键里程碑状态、风险概览
- 任务管理（P0）
  - 任务 CRUD：标题、描述、负责人、成员、计划开始/结束、依赖项、里程碑、优先级、标签、附件
  - 子任务支持（任务分解）
  - 任务依赖关系可视化（简单箭头图）
- 进度与状态（P0）
  - 成员可以更新状态（待开始/进行中/阻塞/已完成/延期）与进度百分比、添加备注与附件
  - 变更历史与审计（谁在何时做了什么）
- 可视化（P0/P1）
  - 看板视图（按状态泳道）
  - 甘特视图（计划与实际/里程碑）
  - 里程碑视图与时间线
- 预警与通知（P0）
  - 规则引擎：逾期预警、计划与实际偏差、关键依赖阻塞
  - 通知通道：站内消息、邮件、Webhook（便于接入企业 IM）
  - 通知接受者灵活设置（负责人、团队成员、指定抄送）
- 权限与组织（P0）
  - 组织/部门结构、角色（管理员/项目负责人/成员/只读）
  - 项目级权限控制（谁能编辑任务、谁能关闭项目）
- 报表与导出（P1）
  - 项目进度报表（完成率、用时、偏差）
  - 成员工作量/负载导出（CSV/PDF）
- 集成（P1）
  - Webhook、API（基础的 REST 接口用于 CRUD、查询、触发通知）
- 管理配置（P1）
  - 通知策略管理、系统设置（工作日/节假日配置）、项目模板
- 审计与合规（P1）
  - 事件审计日志、数据导出与删除机制

每个功能的关键验收标准（选取若干）
- 任务依赖：当任务 A 依赖 B，B 未完成时 A 标示为“有阻塞依赖”；若 B 延期则自动触发 A 的预警。
- 预警投递：预警触发 95% 的测试场景能在规则命中后 30 秒内发出通知（系统性能目标，后端实现时量化）。
- 进度更新历史：每次成员更新将在任务页面保留条目并可回溯，导出包含全部变更记录。

## 4. 产品特定 AI 需求

总体说明：系统可以利用 AI 提供智能预警、自动任务分解、优先级建议与自然语言的进度摘要，但应保持可解释性与可控的规则覆盖优先，AI 建议需明确标注“建议”并允许人工确认。

4.1 模型需求（功能、性能指标）
- 功能
  - 风险预测模型：基于历史项目数据预测某任务/项目逾期概率与风险因子（依赖延迟、成员负载、历史完成率）。
  - 自动任务分解（可选）：将一个项目目标/任务描述自动拆成若干建议子任务与估时建议（为领导提供建议草稿）。
  - 智能摘要：根据任务更新和日志生成日/周进度摘要与待办提醒。
- 性能指标（示例）
  - 风险预测 AUC >= 0.80（在历史数据上验证）或 Precision/Recall 达到可接受阈值（依数据量微调）。
  - 自动拆分建议的人工接受率 >= 60%（可通过 A/B 测试量化）。
  - 摘要生成：用户满意度调查平均评分 >= 4/5（可行性先做小范围试点）。
- 输出格式
  - 风险预测：{risk_score: 0.0-1.0, top_causes: [依赖延迟, 资源不足], confidence: 0-1}
  - 拆分建议：List[{title, estimate_hours, dependencies, confidence}]
  - 摘要：文本 + 结构化要点（阻塞项、需决策点、进展亮点）

4.2 数据需求（来源、数量、质量、标注）
- 来源：平台内历史项目与任务数据、用户更新日志、成员工时记录、外部集成（如工时表）。
- 质量要求：字段齐全（计划/实际时间、负责人、状态变更记录）、时间序列连续性、统一标签/枚举。
- 数量估计：风险模型初步训练建议最少数百个已完成项目且含丰富历史变更；若数据不足，先做规则+少量 ML 混合方案。
- 标注：若做监督学习，需人工标注历史项目是否「成功按期交付/延期/失败」，并标注主要失败原因（依赖、人员、需求变更等）。

4.3 算法边界与可解释性
- 风险模型优先使用可解释模型（如树模型 + SHAP 解释），或在深度模型上补可解释层。
- 所有 AI 建议须提供“原因摘要”（top_causes）与置信度，且在关键自动动作（如自动关闭任务）前必须人工确认。
- 明确不可让 AI 处理权限敏感或合规决策（例如：自动变更负责人、自动删除数据）。

4.4 评估标准
- 离线评估：AUC、Precision/Recall、F1、ROC；业务指标：提前预警命中率、误报率、人工干预率。
- 在线评估：AB 测试，衡量 AI 建议采纳率、任务完成效率（平均延期天数是否下降）、用户满意度。
- 定期回归评估，避免模型随时间降级（建议每 1-3 个月重训练/微调并回测）。

4.5 伦理与合规
- 明确告知用户哪些行为由 AI 提供建议，保留人工不可撤销操作权限。
- 数据权限与隐私：敏感人事信息受限访问，遵守当地法律（例如个人数据删除/导出要求）。
- 模型偏见监控：监控是否对特定成员/部门产出不合理风险评分，提供申诉渠道。

## 5. 非功能性需求（性能，安全，可用性等）
- 可用性/稳定性
  - 系统目标 99.9% 可用（生产环境），关键操作（保存任务/更新状态）延迟 < 300ms（典型场景）。
- 性能
  - 单项目页面加载（含 1000 条任务历史）在 1s 内完成懒加载/分页；后端查询响应 < 200ms（缓存/索引优化）。
- 可伸缩性
  - 支持并发用户规模：初期 500 并发活跃用户，架构需便于扩展（水平扩容）。
- 安全
  - 身份认证支持 SSO/LDAP/OAuth；数据传输 TLS。
  - 细粒度权限控制与审计日志（谁何时修改何项）。
- 可靠性与备份
  - 数据库日备份与每小时增量快照；提供回滚机制与导出功能。
- 国际化与本地化
  - 字符集支持 UTF-8，多语言留接口（中/英首发中文）。
- 可维护性
  - 日志、监控与告警（应用错误、通知失败率、队列积压等）。
- 可用性（UX）
  - 移动端适配（响应式），常用操作 3 步内完成（创建/分配/更新）。
- 隐私与合规
  - 数据删除与导出接口，满足用户隐私请求。

## 6. 发布标准与衡量指标
发布标准（MVP）
- 功能完成度：P0 功能（项目、任务、进度更新、预警、看板/甘特简版、权限）实现并通过验收测试。
- 穩定性：主要流程（创建/更新任务、通知）经过压力测试与端到端测试，关键 bug 阈值为 0 严重、<=3 中等。
- 文档：用户指南（项目管理、通知配置）、管理员指南与发布说明。
- 部署：可在目标环境（云或本地）自动部署并支持回滚。

衡量指标（启动后 30/90 天）
- 活跃度：DAU/MAU；目标：第 30 天 DAU >= 团队规模的 30%（初期）
- 交付改进：目标在 90 天内平均任务延期天数下降 20%（与上线前对比）
- 预警命中率：触发预警后 48 小时内处理（负责人响应/更新）率 >= 70%
- 用户满意度：NPS 或满意度调查平均 >= 7/10
- AI 指标（如启用）：建议采纳率 >= 50%（初期目标）

## 附件：合同式简要输入/输出 & 数据模型建议
“合同”（Contract） — 关键输入/输出/错误模式
- 输入
  - 项目：{id, name, department, ownerUserId, memberUserIds[], planStartDate, planEndDate, milestones[]}
  - 任务：{id, projectId, title, description, ownerUserId, assignees[], planStart, planEnd, dependsOnTaskIds[], status, percentComplete, attachments[]}
  - 用户更新：{taskId, userId, timestamp, status, percentComplete, comment}
- 输出
  - 项目/任务列表、甘特数据（时间序列）、风险分析（score+causes）、通知事件
- 错误模式/边界
  - 依赖环（A 依赖 B 且 B 依赖 A）需在创建时禁止并提示
  - 超出权限的编辑尝试返回 403
  - 时间不一致（计划结束 < 开始）返回校验错误

建议最小数据表（示意）
- users (id, name, email, dept_id, role)
- departments (id, name, parent_id)
- projects (id, name, dept_id, owner_id, plan_start, plan_end, status, created_at, updated_at)
- tasks (id, project_id, parent_task_id, title, desc, owner_id, status, plan_start, plan_end, actual_end, percent_complete, estimate_hours, created_at, updated_at)
- task_dependencies (task_id, depends_on_task_id)
- task_updates (id, task_id, user_id, timestamp, status, percent_complete, comment)
- notifications (id, type, payload, recipients[], status, created_at)

## 关键边界与主要风险（3-5 条）
- 风险：历史数据不足导致 AI 风险模型效果差（缓解：采用规则引擎优先、逐步收集标注数据）。
- 风险：通知滥用或误报导致用户忽视（缓解：允许自定义阈值、抑制重复通知、对通知进行分级）。
- 风险：任务依赖复杂图导致性能问题（缓解：限制单项目最大依赖深度或对复杂图做异步计算）。
- 风险：权限错误导致敏感信息泄露（缓解：实现审计日志与最小权限原则）。

## 验收测试（示例用例）
- 用例 1（任务创建与分配）：创建一个项目并拆成 3 个任务，分配给不同成员，核对任务在被指派用户的任务列表中可见。
- 用例 2（进度更新历史）：成员更新任务状态与进度，检查历史记录能按时间回溯并导出。
- 用例 3（预警触发）：构造依赖任务 B 延期，当 B 延期时，A（依赖）收到阻塞预警并且通知负责人。
- 用例 4（权限校验）：非负责人尝试关闭项目，应被拒绝 (403)。
