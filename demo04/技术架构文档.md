# 技术架构文档

本文档为待办事项（Todo）应用的技术架构说明，覆盖技术选型、数据库表设计（SQL）、REST API 规范、前后端契约、部署与运维建议与可选扩展点。目标是提供一份可执行的工程文档，方便开发、测试与部署。

---

## 1. 概要

这是一个轻量级的待办事项应用示例，满足以下核心需求：

- 展示标题与任务列表
- 输入并添加新任务
- 标记任务为已完成与删除任务
- 支持按“全部 / 未完成 / 已完成”过滤
- 提供批量操作：清除已完成、清除全部

技术栈：

- 前端：React + TypeScript (Vite)
- 后端：FastAPI（Python）
- 数据库：SQLite（开发/小流量场景），生产建议 PostgreSQL
- 接口：RESTful JSON

项目目录建议（已实现）：

- backend/ — FastAPI 服务代码
- front/ — React + TypeScript (Vite) 前端代码

---

## 2. 技术要求（详细）

-- 前端
  - React 18 + TypeScript，使用 Vite（推荐使用 Vite 的 TypeScript 模板）构建开发环境
  - 使用 .tsx/.ts 文件；添加 `tsconfig.json` 并在 package.json 中包含 TypeScript 开发依赖：`typescript`、`@types/react`、`@types/react-dom`（或使用对应的工具链）
  - CSS：现代、简洁，响应式，主体居中且最大宽度 800px
  - 与后端通过 REST API 通信；支持 VITE_API_BASE 环境变量

- 后端
  - FastAPI，提供 JSON REST 接口
  - SQLAlchemy 作为 ORM（可选直接使用 pydantic + raw SQL）
  - 支持 CORS（开发模式可允许全部 origin）
  - 数据库连接通过环境变量 DATABASE_URL 配置

- 数据库
  - SQLite（文件 todo.db）用于快速开发
  - 表设计需包含 id、title、description（可选）、completed、created_at、updated_at
  - 生产建议迁移至 PostgreSQL，并使用 Alembic 管理迁移

## 3. 数据库设计（SQL）

下面给出兼容 SQLite 的建表语句，包含时间戳与更新触发器：

```sql
-- todos 表
CREATE TABLE IF NOT EXISTS todos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  description TEXT DEFAULT NULL,
  completed BOOLEAN NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT (datetime('now')),
  updated_at DATETIME NOT NULL DEFAULT (datetime('now'))
);

-- 可选触发器：在更新时自动刷新 updated_at
CREATE TRIGGER IF NOT EXISTS todos_updated_at
AFTER UPDATE ON todos
BEGIN
  UPDATE todos SET updated_at = datetime('now') WHERE id = NEW.id;
END;
```

字段说明：

- id：主键，自增
- title：任务标题，非空
- description：任务详情，可选
- completed：布尔，0/1 表示未完成/已完成
- created_at / updated_at：时间戳

注意：若迁移到 PostgreSQL，建议把 `BOOLEAN` 类型使用 PostgreSQL 的 boolean 并把默认时间改为 now()；并引入 Alembic 管理 schema 变更。

## 4. REST API 规范

通用说明：

- 所有请求与响应均采用 JSON。
- 后端基础路径：`/api`。
- 成功返回 HTTP 2xx，失败返回合适的 HTTP 状态码和 JSON 错误信息（{ "detail": "..." }）。

以下列出具体的端点、请求/响应示例和行为说明。

### 4.1 列出 Todos

- 方法：GET
- 路径：`/api/todos`
- 描述：返回所有 Todos，默认按创建时间或 id 排序（可拓展分页与过滤）。
- 请求参数（可选，未来扩展）：
  - `?filter=all|active|completed`
  - `?page=` / `?limit=` 分页
- 成功响应示例（200）：

```json
[
  {
    "id": 1,
    "title": "买牛奶",
    "description": null,
    "completed": false,
    "created_at": "2025-10-02 10:00:00",
    "updated_at": "2025-10-02 10:00:00"
  }
]
```

### 4.2 创建 Todo

- 方法：POST
- 路径：`/api/todos`
- 请求头：`Content-Type: application/json`
- 请求体示例：

```json
{ "title": "写技术文档", "description": "撰写架构说明" }
```

- 成功响应（201 或 200）：返回创建的 Todo 对象

响应示例：

```json
{
  "id": 2,
  "title": "写技术文档",
  "description": "撰写架构说明",
  "completed": false,
  "created_at": "2025-10-02 12:00:00",
  "updated_at": "2025-10-02 12:00:00"
}
```

错误示例（422，校验不通过）：

```json
{ "detail": [ { "loc": ["body","title"], "msg": "field required", "type": "value_error.missing" } ] }
```

### 4.3 更新 Todo（部分或全量）

- 方法：PUT
- 路径：`/api/todos/{todo_id}`
- 请求体示例（可部分更新）：

```json
{ "title": "新的标题", "completed": true }
```

- 成功响应（200）：返回更新后的对象

错误示例（404）：

```json
{ "detail": "Todo not found" }
```

### 4.4 删除 Todo

- 方法：DELETE
- 路径：`/api/todos/{todo_id}`
- 成功响应（200 / 204）：

```json
{ "ok": true }
```

### 4.5 清除已完成

- 方法：POST
- 路径：`/api/clear_completed`
- 描述：删除所有 completed = true 的记录
- 成功响应：{ "ok": true }

### 4.6 清除全部

- 方法：POST
- 路径：`/api/clear_all`
- 描述：删除所有记录，危险操作，应在生产环境中加权限或确认机制
- 成功响应：{ "ok": true }

## 5. 前后端数据契约（示例接口数据模型）

前端与后端共享的 Todo 数据结构：

```ts
interface Todo {
  id: number;
  title: string;
  description?: string | null;
  completed: boolean;
  created_at?: string;
  updated_at?: string;
}
```

前端行为说明（对照用户需求）：

- 添加：点击添加后调用 POST /api/todos，成功后把返回对象插入到列表并清空输入框。
- 完成/取消：点击“完成”发送 PUT /api/todos/{id} 更新 completed 字段，成功后更新 UI（对 completed 的条目添加 `completed` class）。
- 删除：点击“删除”发送 DELETE /api/todos/{id}，成功后从列表移除。
- 过滤：前端可本地实现过滤（all/active/completed），或由后端通过查询参数支持过滤。
- 批量清理：调用 /api/clear_completed 或 /api/clear_all，然后刷新或更新前端列表状态。

错误处理建议：

- 网络错误：提示并允许重试。
- 校验错误：显示后端返回的字段级错误。
- 删除/更新失败（并发或 404）：通知用户并刷新列表以获得最新数据。

## 7. 安全、部署与运维建议

- CORS：开发时允许所有 origin，生产时限制为可信域名。
- 数据库：生产环境使用 PostgreSQL/MySQL，保证并发与备份策略。
- 日志与监控：后端引入 structured logging、健康检查端点 `/health`，并接入监控（Prometheus/CloudWatch 等）。
- 备份：SQLite 文件需定期 snapshot；若改 PostgreSQL，使用定期备份与 WAL 归档策略。
- 生产部署：后端运行在 ASGI 容器（uvicorn/gunicorn），前端构建产物由 CDN/静态服务器（Nginx）提供。
